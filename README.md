# Agentic-Chat

An AI copilot for an enterprise demand forecasting platform: ask natural-language
questions about demand, sales revenue, forecast accuracy, inventory/stockout risk,
demand pattern classification, or replenishment orders, and get back a plain-English,
role-appropriate answer generated from a live SQL query — plus optional voice input
and spoken responses.

**Stack:** Flask (Python) API + SQLite, React (Vite) frontend.

## Where this came from

This started as a from-scratch build modeled on a reference Angular + .NET/SQL
Server "AI agentic chat" implementation for a hospital management system, then was
retargeted mid-build to a demand-forecasting domain instead. The architecture
(NL question -> LLM-classified intent -> schema-grounded NL->SQL generation ->
SQL validation -> execution -> LLM-explained answer) is a direct port of that
reference's `AIDataQueryService.cs`, adapted from SQL Server/T-SQL to SQLite and
from a hospital schema to a demand-forecasting one.

## Architecture

```
frontend/   React + Vite chat UI (AiAgenticChat component), talks to the backend
            over /api/* (proxied to Flask in dev by vite.config.js)
backend/
  app/
    models.py            SQLAlchemy models for the demand-forecasting schema
    schema/
      demand_forecasting_schema.json   The same schema, richly annotated
                                        (business rules, synonyms, FKs) and fed
                                        directly into the LLM prompt so the
                                        model only ever sees real tables/columns
    seed.py               Populates SQLite with a plausible year of demo data
    services/
      llm_provider.py            Provider-agnostic chat-completion client
      tts_provider.py            gTTS (default, free) or Sarvam AI TTS
      ai_data_query_service.py   The ported core: intent detection, safety
                                  guardrails, SQL generation/validation/repair,
                                  execution, result explanation
    routes/                Flask blueprints: /api/agent, /api/tts, /api/health
```

## Deliberate deviations from the reference implementation

- **SQLite instead of SQL Server.** All T-SQL-specific syntax in the prompt
  (`GETDATE()`, `DATEADD`, `DATEFROMPARTS`, `TOP N`, `ISNULL`, `AT TIME ZONE`) was
  rewritten to SQLite equivalents (`date('now','localtime', ...)`, `LIMIT`,
  `IFNULL`). See Section 8 of the SQL-generation prompt in
  `ai_data_query_service.py`.
- **No hardcoded API keys.** The reference code had a Sarvam AI subscription key
  committed directly in the Angular component. Every credential here (LLM
  provider, Sarvam) is read from an environment variable via `backend/.env`
  (see `backend/.env.example`) and the app runs (with a clear in-chat error)
  even if none are set.
- **Speech-to-text uses the browser's native `SpeechRecognition` API** instead of
  a custom WebSocket bridge to a streaming STT vendor. The reference implementation
  actually had this same fallback written (commented out) in its Angular
  component; it was promoted to the primary (and only) implementation here
  because it needs no backend audio pipeline or vendor key to work. The mic
  button's waveform visualization is still a live Web Audio `AnalyserNode`
  render loop, ported from the original canvas drawing code.
- **Text-to-speech defaults to gTTS** (free, no API key) instead of requiring
  Sarvam. Set `TTS_PROVIDER=sarvam` and `SARVAM_API_KEY` in `.env` to switch.
- **Demo data is synthetic**, generated by `backend/app/seed.py` with dates
  relative to "now" so date-scoped questions ("today", "this month") return
  sensible results whenever you run it.

## Running locally

### Backend

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # then set AI_API_KEY (or OPENAI_API_KEY/ANTHROPIC_API_KEY)
python -m app.seed     # creates backend/instance/agentic_chat.db with demo data
python run.py          # serves on http://localhost:5000
```

The AI assistant needs an LLM key to do anything beyond greetings — without one
it responds with a clear in-chat error explaining what to set.

### Frontend

```bash
cd frontend
npm install
npm run dev             # serves on http://localhost:5173, proxies /api to :5000
```

Open http://localhost:5173, pick a role from the top-right dropdown (Demand
Planner / Supply Planner / Category Manager / Analyst / Executive / Admin — this
drives which tables the assistant is allowed to touch), and ask a question.

### Try asking

- "What was total demand last week?"
- "Which products are at risk of stockout?"
- "What's the forecast accuracy for the latest run?"
- "Show me open replenishment orders"
- "Which category had the highest revenue this month?"

## Security notes

- SQL generation is schema-grounded and validated: the LLM's SQL is re-checked
  against the actual schema (tables/columns must exist), `SELECT *` and any
  non-`SELECT` statement is rejected, and a row `LIMIT` is enforced.
- Role-based access is enforced twice: before generation (question mentions a
  restricted table) and after (generated SQL touches a restricted table).
- A battery of regex guardrails blocks SQL-injection-shaped input, schema-probing
  questions ("list all tables"), and sensitive-data requests (credentials, etc.)
  before they ever reach the LLM.
